# Agent Note：Team workspace 在实际运行中暴露的问题

Status: implemented

[English](2026-09-01-team-workspace-motion-and-controls.md) | 中文

## Problem

五项功能落在 Team workspace 上 —— 记录时间线、按成员的投入、成员工作的 tail、被执行的 write scope，以及 follow stream。随后用桌面应用对真实 Team 运行，暴露出一组测试无法指认的缺陷：每一个都关乎界面随时间的行为，而非它渲染了什么。

成员 card 携带一个通用的人形轮廓，对每个成员完全相同 —— 而这个界面的全部职责就是把他们区分开。card 的宽度动画很平滑，随后却在两个不同位置各自「咔」地一跳。每一行时间线都渲染实时的像素追逐标记，于是一条十分钟前就已完成的任务记录，看上去仍像在进行中。展开只能靠 hover，而当指针落到一张仍在其下方增长的 card 之外时 hover 就会丢失 —— 与此同时，点击（本该是把 card 固定打开的显而易见的方式）却会把人带离 workspace。header 宣告了一个别处从不使用的 Team 名称，并携带一个「没有任何东西能与之矛盾」的徽章。添加共享任务则要求手动输入 task id 与以逗号分隔的路径。

## Decision

**成员由其名字所述的角色来标记。** teammate 的名字就是它被创建时所承担的角色，因此名字的首字母就是角色：`writer` 读作 W，`code-reviewer` 读作 CR。它取代了任何 agent 都没有的头像，并且是 glyph 中唯一按成员而非按席位位置变化的部分。不同角色配不同图形图标的方案被否决：teammate 名字是模型自由选择的文本，任何图标映射都只能靠猜。

**动效意味着确有工作在进行。** 处于 running 或 provisioning 的成员会让 glyph 的内环扫描、标记绕行，并从图形中扩散出一圈涟漪。idle、failed 与 inactive 的成员保持静止图形，因此 roster 上的动效承载状态，而不是对每张 card 一视同仁的装饰。reduced motion 会让它们全部停下。

**时间线中的任何东西都不动。** 每一行都是已经发生过的事实。实时标记在此声称某项工作仍在运行 —— 而它在读者到来之前就已结束；静态标记用于区分失败、已了结的变化，以及其余记录。

**结构性的布局变化，正是过渡动画无法承载的东西。** 两处跳动是同一类缺陷出现在不同位置，且都不是时序问题：

- 详情框在 card 仍在做宽度动画时，于一帧之内离开了布局流。它现在按高度、外边距与内边距一同开合，并在移动过程中裁剪内容。
- 角色标签与状态共用一个会换行的行，因此状态会在宽度动画中途换行。它们现在在任何宽度下都保持两行。

第三处则是通过消除变化而非为其添加动画来解决：tail 的各行是在 card 展开之后才从各自的读取中到达的，因此 tail 位于一个高度与已到达行数无关的视窗中。

**点击将展开锁定；导航成为独立控件。** 点击会把 card 固定打开，直到再次点击；释放时同时丢弃 hover 预览，这样释放它的那次点击就不会通过它刚获得的焦点把它继续撑开。打开 teammate 会话移到了 message 与 interrupt 旁边的控件上，因此阅读某个成员不会再意外离开 workspace。所有 card 都可展开，包括 failed 与 provisioning 的 —— 因为诊断信息正位于它们的详情之中。

**任务从看板构建。** 依赖按 subject 从已存在的任务中选取 —— id 是看板从不展示的值，读者不得不去别处查找 —— 且任务永远不会把自己列为可选项。write scope 逐条路径添加、以 chip 形式移除，这也意味着编辑任务会保留它已经声明的 scope，而不必重新键入整份清单。

## Alternatives considered

**为 tail 的到达在详情框上使用 `layout`。** 这是教科书式的答案，而它**冻结了 renderer**。在详情框已有的 `height: auto` 动画之上，它会自我反馈；在回退之前，页面的每一次截图都会超时。没有别的东西能发现它 —— 测试通过、类型检查干净 —— 因此把它记录在此，而不是留给下一位读者重新发现。

**用 `:has()` 控制正在撰写的 card 宽度。** 选择器确实匹配（`element.matches()` 返回 true，规则在页面中，其特异性也胜出），而 card 依然从未被重新计算样式：表单出现在其下方时，Chromium 没有触发失效。改为由界面自身的 state 属性驱动 —— 这也是该组件其余部分本就采用的方式。

**保留标题与徽章。** 否决：workspace 只在有 live session 时才渲染，因此该徽章断言的是没有任何东西能与之矛盾的事情，而页脚已经承载实时指示。Team 的名字就是它的 roster。

**像 tail 一样为投入行预留空间。** 否决：投入缺失意味着「缺失」，而非零；占位符会与之矛盾。

## Consequences

展开的 card 有一块固定的 tail 区域，因此没有任何记录的成员会显示一个空视窗，而不是一行文字。这是「card 绝不在读者眼下移动」的代价。

角色标签与状态不再在空间足够时共用一行，因此宽 card 的状态旁会留有空白。在任何宽度下都保持稳定，比在某一个宽度下更紧凑更有价值。

`TeamMemberView.pendingMessages` 是必填的，因此 client 测试中每一个手工构造的成员视图都要携带它。

看板 fixture 增加了第二个任务，因为依赖需要有可依赖的对象。这让原本无歧义的查询变得有歧义 —— 两个 Edit 按钮、两个 owner 选择框 —— 因此六个测试会把查询限定到它们所指的那张 card。其中一个无法按 subject 来定位那张 card：subject 会在测试中途改变，而一旦该任务依赖了另一个任务，它的 card 也会写出对方的名字，所以改为按 task id 查找。

## Testing

Client 测试覆盖：单词名、连字符名与单字符名的 monogram；running 与 provisioning 成员带有工作标记而 idle 与 failed 成员没有；每一行时间线的静态标记，且其中不存在任何实时标记；tail 的分阶段显现及其 reduced-motion 形态；点击锁定、释放，以及在指针离开 roster 后依然保持展开；从独立控件发起导航，以及对不可达 teammate 不提供该控件；还有任务表单选择与取消选择 blocker、通过 Enter 与按钮添加 scope、拒绝空输入、移除 chip。收起的平滑度与标记的适配是在运行中的应用里测量的，而非在 jsdom 中断言 —— 后者不渲染几何。
